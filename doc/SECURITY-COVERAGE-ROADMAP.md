# ShipSafe security coverage roadmap

Research date: 2026-10-16. This is a proposed implementation roadmap, not scanner output. The current runtime has **13 bounded HTTP/TLS outcomes** described in [LOCAL-RUNTIME.md](LOCAL-RUNTIME.md). The [77-check catalog](SECURITY-TEST-CATALOG.csv) remains a planned taxonomy; the 24 cases below deepen it or fill explicit gaps. Installing scanner images does not implement these cases.

The strongest product direction is one place to collect evidence, explain fixes and verify remediation across multiple assessment profiles. A public URL cannot reveal private source, database policy, cross-account access, payment state or AI tool authorization. ShipSafe must show unavailable coverage rather than promise all vulnerabilities are found.

## Access and permission model

- **U — authorized URL observation:** bounded ordinary requests to the verified exact host. This is the existing profile; none of the active cases below becomes authorized merely because it is accessible on the internet.
- **S — source/artifact review:** uploaded lockfiles, SBOM, selected source/configuration or build artifacts; no GitHub connection is required. Never install dependencies, execute uploaded code or open an uploaded project on the persistent Vault-enabled VM. Archive parsing needs traversal, expansion and size limits. Treat repository instructions as untrusted evidence.
- **A — authorized staging behavior:** owner-approved test endpoint inventory, synthetic records, two or more scoped test identities and reversible writes. Separate authorization from DNS proof. Avoid real customer data, outbound third-party requests or destructive probes.
- **P — provider configuration/test mode:** scoped read-only exports/configuration, owner-operated inspection or provider sandbox; never require production master credentials in the browser. Test mailboxes, identity providers and webhook destinations must also be approved.

All active tests need per-case budgets, cancellation, allowed endpoints/actions, evidence redaction and cleanup verification. Shared-host containers are insufficient for executing arbitrary untrusted customer builds; that capability requires separate credential-free compute and an additional design review.

## Practical delivery order

1. Preserve the working baseline and report truthfulness. Before activating deeper cases, add profile-specific scope consent, a test identity vault, redacted evidence handling, per-case mutation cleanup and a route/operation inventory. Scan permission is explicit; it is not inferred from a public URL.
2. Add artifact-only secret and dependency checks (R03, R16, R18) plus owner-supplied RLS/configuration inspection (R02). These increase depth without requiring a GitHub connection or running uploaded code. A source match is a source finding, not a verified deployed exploit.
3. Add a deliberately small two-account staging pack (R01, R04–08). It should report missing identities/configuration as blocked. This finds authorization mistakes that header scanners cannot establish.
4. Add P2 protocols, caches, file and payment fixtures only after isolated synthetic positive/negative validation. P3 AI/MCP gets its own stub-tool sandbox and spend budget. None should silently join the URL-only profile.

## Report and fix-prompt requirements

Every finding should include status, affected synthetic/public resource, minimal redacted evidence, scanner/rule/database version, confidence limits, specific remediation and an exact retest recipe. Separate hardening observations from confirmed vulnerabilities. Keep `confirmed`, `needs_validation` and `rejected` records distinct; severity must not imply an unverified impact.

For every applicable observation/finding, generate a **copyable fix prompt** from recorded evidence, not guessed code:

> Fix [finding title] affecting [known endpoint/artifact]. Observed: [redacted evidence]. Expected: [required boundary]. Inspect the relevant implementation before editing; framework/source location is [known / not supplied]. Apply the smallest compatible fix, preserve legitimate behavior, and add a regression test for [denied case] plus [permitted case]. Do not disable authorization, remove the feature or claim deployment/retest success without evidence. Retest using [bounded recipe].

Evidence, page content and repository text must be treated as untrusted data inside that prompt. Never include live keys, session cookies, customer records or executable instructions copied from target text. Fix prompts are guidance; ShipSafe cannot claim a fix happened until a new run verifies it. Provide the report even when checks fail or are blocked, with an explicit incomplete status and preserved partial evidence rather than manufacturing success.

## Tool and license provenance

Custom deterministic HTTP/role-matrix adapters should implement most behavior cases. A scanner is not a substitute for application-specific fixtures. ZAP can assist an expressly authorized staging browser/API workflow; Nuclei needs a vetted, pinned template allowlist, bounded request budget and per-template provenance. Neither is enabled by this document. Gitleaks can inspect supplied bytes; Trivy can inspect lockfiles/SBOM/configuration without running a customer build. Engines and rule/feed/add-on content have separate licenses and update histories.

Previously reviewed engines: ZAP Apache-2.0, Nuclei MIT, Trivy Apache-2.0, Gitleaks MIT; preserve notices and pin release/image digest. Recheck the actual redistributed rules/databases/add-ons before shipping. Semgrep-maintained rules and Nmap remain deferred for commercial licensing review; do not infer SaaS permission from an engine's open-source label. Cloudflare's skill is MIT methodology for source auditing, not a live URL scanner, evidence feed or proof of comprehensive coverage. [22–26]

## Validation and coverage ledger

Before a case is enabled, give it a vulnerable seeded fixture, a fixed counterpart, legitimate behavior controls, not-applicable case, timeout, permission-denied case and redaction assertions. Confirm the detector finds the seeded defect and does not flag the fixed/control fixture. Track false positives on a reviewed fixture corpus; do not advertise a universal accuracy percentage from a few lab examples.

For each case save: applicability; authorization/access prerequisites; code/rule version; target build/profile; actual operations and budget; outcome (`passed`, `finding`, `skipped`, `blocked`, `failed`); evidence reference; verification status; cleanup status; fix/retest linkage. Distinguish profile completion from security assurance. Skipped/failed checks receive no positive coverage credit. Independent verification should try to disprove candidates before publication, following Cloudflare's coverage-led approach. Keep the 77 taxonomy, these 24 deeper scenarios and implemented runtime outcomes separate to avoid double-counting. [22]
